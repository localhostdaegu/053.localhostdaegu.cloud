## 테스트 범위와 개발 아키텍처

단위 테스트 → 모듈 통합 테스트 → 사용자 시나리오 → 성능·예외 테스트 순서로 진행합니다. 대상 구성은 [상위 설계]({{ '/docs/architecture/' | relative_url }})에 연결하고, 구현 시점의 실제 구조와 버전을 기록합니다.

## 사전 준비사항

- 선정된 기능과 지원 입력 형식
- 정답·기대 결과가 있는 테스트 데이터
- 코드·모델·라이브러리·데이터 버전
- 실행 환경과 설정
- 외부 API의 실제 호출 여부 또는 모의 응답 사용 여부
- 기능별 통과 기준과 성능 목표값

현재 테스트 데이터와 수치 기준은 미정이며, **서비스 테스트는 실행하지 않았습니다.**

## 단위 테스트 — 하나의 처리 규칙

아래 값은 판정 방법을 설명하기 위한 가상 샘플입니다. 실제 입력 형식과 규칙을 확정한 뒤 테스트 데이터로 구체화합니다.

| 번호 | 대상 | 입력 예시 | 기대 결과 제안 | 상태 |
|---|---|---|---|---|
| UT-001 | M1 매출 합계 계산 | 같은 기간의 10,000원·20,000원 2건 | 중복·취소 없는 샘플에서 합계 30,000원 | 미실행 |
| UT-002 | M2 지역 조건 비교 | 대상 지역 대구 / 입력 지역 대구와 부산 각각 | 대구는 지역 조건 충족, 부산은 불충족 사유 표시 | 미실행 |
| UT-003 | M3 지표 계산 | 이전 기간 100, 비교 기간 120 | 동일 기준의 증가율 20%; 이전 값 0은 별도 처리 | 미실행 |
| UT-004 | M0 필수 입력 검증 | 필수 항목 누락 | 필요한 항목을 반환하고 후속 처리를 호출하지 않음 | 미실행 |

## 통합 테스트 — 모듈 연결과 외부 의존성

| 번호 | 연결 경계 | 준비·입력 | 기대 결과 제안 | 상태 |
|---|---|---|---|---|
| IT-001 | M0 → 선정 기능 → M4 → 결과 화면 | 샘플 요청과 출처가 있는 응답 | 입력 조건·처리 결과·출처가 전체 흐름에서 보존 | 미실행 |
| IT-002 | 기능 모듈 → 데이터 API | API 오류 또는 타임아웃 모의 응답 | 실패를 결과 화면까지 전달하고 성공으로 기록하지 않음 | 미실행 |
| IT-003 | 기능 처리 → AI 추론 → 결과 검토 | 알려진 처리 결과와 근거를 모델에 전달 | 집계값과 출처를 유지하고 확인되지 않은 항목을 구분 | 미실행 |

통합 시험에는 실제 API와 모의 응답 중 무엇을 사용했는지 기록합니다. 단위·통합 검증 후 아래 사용자 시나리오를 실행합니다.

## 성능 측정 계획

TPS의 의미를 먼저 정의합니다. **API 요청 처리량(req/s), 거래 처리량(tx/s), 모델 토큰 생성 속도(token/s)**는 별도 지표로 기록합니다. 적용하지 않는 지표는 이유와 함께 해당 없음으로 표시합니다.

| 측정 구간 | 지표 후보 | 필요한 조건 | 결과 |
|---|---|---|---|
| 데이터 조회 | 지연·실패율 | 데이터 크기·캐시 조건·동시 요청 | 미측정 |
| AI 추론 | 응답 지연·토큰 생성 속도 | 모델·입출력 크기·실행 장치 | 미측정 |
| 전체 요청 | 처리량·p50/p95 응답시간·실패율 | 동시 사용자·지속 시간·환경 | 미측정 |

p95 응답시간은 요청 100건 중 약 95건이 그 시간 안에 끝났다는 뜻입니다. 목표값은 측정 전에 합의하고, 실측값과 구분합니다.

## 결과 기록 형식

테스트 ID / 실행일 / 코드·모델 버전 / 데이터 / HW·SW / 설정 / 절차 / 기대 결과 / 실제 결과 / 판정 / 로그 / 결함 / 재검증 결과를 기록합니다.

고객 환경 구축·이전 후 테스트가 필요한지는 검수 범위에서 결정합니다. [최종 검수]({{ '/docs/acceptance/' | relative_url }})에 해당 여부와 이유를 남깁니다.
